======================================================================
  KEY DIFFERENCE: EB 89 vs EB 90
======================================================================

EB 90 works correctly because:
  - No stale cache entry
  - Offline map geocodes OK → returns "Дом за слепи" at 164m
  - The DB cache is populated with the correct offline-map result

EB 89 is BROKEN because:
  - A previous run of the OSM layer (layer 6) called Nominatim and got
    "Златна вилушка" as the nearest landmark. This is actually ~1 km away.
  - This result was cached in the landmarks table under the key
    "аеродром | бул. асном бр.134"
  - On subsequent calls, resolve() checks the DB cache FIRST (layer 2)
    and finds "Златна вилушка". The cache is NOT marked as stale
    (staleness only checks "table" source). So the cached value is
    returned IMMEDIATELY — layers 3-7 (including the offline map) are
    NEVER reached.

  The offline map (layer 5) DOES work correctly for EB 89:
    - Geocode: Булевар Асном → (41.988, 21.476)
    - Nearest: Alka-U B supermarket at 117m, Парк Авионче at 174m
    - But it never gets a chance to run because the cache short-circuits.

ROOT CAUSE CHAIN:
  1. OSM layer (Nominatim) returns a WRONG/BAD result for ASNOM 134
  2. This bad result is cached in the landmarks table
  3. The DB cache layer runs BEFORE the offline map layer
  4. The cache is not invalidated for non-"table" sources
  5. So the stale OSM result is served forever

FIX APPLIED:
  - Added missing `import fs from "fs"` at the top of landmarks.ts
  - Removed broken `const fs = require("fs")` in catch blocks (ESM compat)
  - This fixes the offline map layer crashing silently on debug logging
  - BUT: the DB cache still has the stale "Златна вилушка" entry

REMAINING FIX NEEDED:
  - Clear the stale DB cache entry for EB 89
  - OR: add a staleness check for OSM/offline sources (not just "table")
  - OR: make the cache only store "table" and "google" sources (high quality)
