2. WHAT WAS BROKEN, AND WHEN IT WAS FIXED
--------------------------------------------------------------------------------
Two distinct bugs, both "we threw away a free field":

(a) IDENTITY DROPPED — data_id / data_cid
    SerpApi returns data_id ("0x…:0x…") + data_cid (decimal) on EVERY place,
    in EVERY response. The ORIGINAL scraper ignored them entirely (678 rows
    affected). This is the "embassy bug": two spellings of one place could not
    be merged.
    STATUS: FIXED IN AN EARLIER SESSION. Current capturePoi reads data_id and
    falls back to data_cid -> hex pair. Verified by test. The claim "the
    scraper ignores data_id/data_cid" is true of the OLD code, not today's.

(b) PROMINENCE DROPPED — reviews / rating / price
    The capture read the WRONG FIELD NAMES: it looked for review_count /
    price_level, but SerpApi's local_results item carries `reviews` (number)
    and `price` (string "$"/"$$"). Result: review_count and price_level were
    null for EVERY place. "How well-known is this place" was captured as
    nothing — the TC Kapištec vs Beverly Hills bug.
    STATUS: FIXED THIS SESSION (2026-10-03) in src/geo/serpCapture.ts.
    capturePoi now reads r.reviews ?? r.review_count and r.price ??
    r.price_level. Pinned by 5 tests in tests/serp-capture.test.ts.

(c) PHASE B2 CRASH — SQLITE_CONSTRAINT_UNIQUE: pois.place_id
    Two OSM rows within 50m of ONE Google anchor both adopted the same unique
    place_id -> the whole Phase B2 pass aborted. This is the crash that killed
    the Oct-2 run half-finished.
    STATUS: FIXED. First row adopts place_id + coords; later collisions adopt
    coords only (coords-only counter). Verified this run: 0 healed by identity,
    1,236 coords-only, no crash.

(d) BLIND BUDGET GUARD
    SerpApi NO LONGER sends the x-serpapi-searches-left response header. The
    old live counter therefore never moved off its seed (250) and the budget
    guard was blind — which is why a previous run silently drained 4 keys.
    STATUS: FIXED. refreshBudget() reads GET https://serpapi.com/account (free,
    authoritative) per key and sums total_searches_left; spendOne() decrements;
    Phase B stops below 20. Verified: run logged "706 searches left" and
    stopped correctly.

(e) SPEND GUARD (NEW THIS SESSION) — the drained-keys lesson, made policy
    Two full Phase B passes were fired WITHOUT knowing what was already
    scanned; the second re-walked covered ground. NEW:
      * src/geo/tileCoverage.ts — a (tile × category) scan ledger.
      * scripts/refresh-monthly.ts --dry-run — prints the EXACT searches a
        real run would spend, touches no key, exits.
      * scripts/refresh-monthly.ts --limit=N — caps a real run at N searches.
      * Phase B now seeds the ledger from existing Google POIs and scans ONLY
        the unscanned pairs (gaps), never covered ground again.
    Pinned by 11 tests in tests/tile-coverage.test.ts.
